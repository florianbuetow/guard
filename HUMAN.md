# Explanation Artifact: Guard

**What is this**
I built Guard, a terminal-based tool with both a CLI and a TUI for marking files or collections of files as guarded so AI coding agents running as my user cannot modify them without elevated privileges. It solves a very literal problem: when I let an agent work in a repository, I do not want it silently changing files like configuration files, tests, or prompt files that I consider out of bounds. Instead of relying on the agent to behave, I use filesystem-level protection so the restriction is enforced by the OS. In practice, this lets me let the agent roam more freely while keeping specific files locked down.

**Why this approach**
I chose Go over Python, JavaScript, or Java because it gave me the filesystem and terminal primitives I needed without extra dependencies, and it produces a fast compiled binary instead of a script. I chose filesystem attributes rather than ordinary read-only permissions because same-user agents can usually undo normal file permissions, while the attribute-based approach raises the bar to superuser privileges on supported Unix-like systems. I deliberately did not build a GUI or an AI layer that decides what should be locked, because both would add complexity and weaken the trust boundary; I want the user to decide what gets protected. AI accelerated implementation, test generation, and iteration inside a structure I defined, but the architecture, tutorials, behavioral specs, and guardrails were my decisions.

**What would break**
The strongest guarantee depends on the underlying filesystem and OS actually honoring the attributes I rely on; when that support is missing, Guard can warn loudly but it cannot enforce protection. The tool also depends on its own guard file, so if that file is corrupted I can lose the previous permission state and recovery becomes manual. Its safety model only holds against same-user agents on supported systems; if an agent runs with superuser privileges, or the user intentionally removes the guard first, the protection no longer means much. The hardest area for me to debug manually is the TUI, because its behavior is visually intricate and tightly coupled, so my confidence there comes more from end-to-end and visual tests than from line-by-line code familiarity.

**What I learned**
I started out thinking that a clear specification would be enough to get good implementations from AI, and that turned out to be wrong. What actually worked was specification plus end-to-end tests plus static guardrails, because the models needed constraints on both behavior and code quality to stay on track. I also learned that model capability varies a lot: some agents got stuck in loops even with specs and tests, while stronger ones still produced bad structure when my architecture was underspecified and they mixed storage with business logic. If I started over, I would keep the tutorial-first, behavior-first workflow, but I would define module boundaries earlier, add architectural unit tests, and automate more of the implementation and review loop.

This explanation artifact exists so the reasoning behind the project travels with the code itself. It is meant to be attached to the work wherever the work is shown: in this repository, in a project profile, or on a personal site.
